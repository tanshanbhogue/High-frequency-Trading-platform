# Database design overview

## Problem statement
A High Frequency Trading (HFT) desk needs one reliable place to record **who** trades **what**, **where** and **how much**: traders place orders for portfolios they own, orders may be generated by algorithms, orders are routed to one or more exchanges, and every execution is recorded as a trade. Market quotes are stored per security listing, and algorithms can be trained on those quotes.

## Entities (8) and junction tables (6)

| Entity | Purpose |
|---|---|
| `traders` | People on the desk (name, desk, role, status, optional manager `reports_to`) |
| `algorithms` | Trading algorithms, unique by (name, version) |
| `portfolios` | Investment portfolios (currency, risk profile) |
| `securities` | Stocks / ETFs, unique ISIN |
| `exchanges` | Trading venues, unique MIC code |
| `orders` | A trader's instruction to buy or sell a security for a portfolio |
| `trades` | One execution of (part of) an order on one exchange |
| `market_feed_data` | Timestamped bid/ask/last quote for one security on one exchange |

| Junction | Relationship | Extra attributes |
|---|---|---|
| `portfolio_owners` | Trader ↔ Portfolio | `ownership_percentage`, `ownership_start_date` |
| `algorithm_developers` | Trader ↔ Algorithm | `contribution_role`, `developed_at` |
| `portfolio_holdings` | Portfolio ↔ Security | `quantity_held`, `avg_price` |
| `security_listings` | Security ↔ Exchange | `ticker_symbol`, `listing_date`, `currency` |
| `algorithm_training_data` | Algorithm ↔ Market feed | `data_split` |
| `order_routes` | Order ↔ Exchange | `routed_quantity`, `route_status`, `routing_reason` |

Supporting tables added for the application: `app_users` (web logins, bcrypt hashes) and `audit_log` (filled by triggers).

## The five relationship labels from the original ER diagram
| Diagram label | Implemented as |
|---|---|
| Trader **OWNS** Portfolio | `portfolio_owners.ownership_percentage` |
| Order **EXECUTES AS** Trade | `trades.executed_quantity` (one order → many trades) |
| Security **LISTED ON** Exchange | `security_listings.ticker_symbol` |
| Security **QUOTES** Market feed | `market_feed_data.feed_timestamp` (the quote timestamp), through the listing |
| Trade **EXECUTED_ON** Exchange | composite FK `trades(order_id, exchange_id)` → `order_routes(order_id, exchange_id)` |

## Two key design decisions
1. **A trader may only order for a portfolio they own** — `orders(trader_id, portfolio_id)` is a composite foreign key to `portfolio_owners(trader_id, portfolio_id)`.
2. **A trade can only happen on an exchange the order was routed to** — `trades(order_id, exchange_id)` is a composite foreign key to `order_routes(order_id, exchange_id)`.

## Integrity summary
Primary keys on every table (composite on junctions) · foreign keys with explicit `ON DELETE` / `ON UPDATE` actions · `UNIQUE` on email, ISIN, MIC, (algorithm name, version), (exchange, ticker), (security, exchange), execution reference · `NOT NULL` on mandatory data · `DECIMAL` for money and quantities · `CHECK` for positive quantities/prices, bid ≤ ask, 0 < ownership ≤ 100, valid statuses/enums · triggers for rules that need other rows (see `03_relational_schema.md`).
